# 推理优化

> 两个阶段定义 LLM 推理。预填充并行处理你的提示——计算受限。解码逐个生成 Token——内存受限。每个优化都针对一个或两个。

**类型:** 构建
**语言:** Python
**前置要求:** 第10阶段，第01-08课（Transformer 架构、注意力）
**时间:** ~120分钟

## 学习目标

- 实现 KV 缓存以消除自回归 Token 生成期间的冗余计算
- 解释 LLM 推理的预填充与解码阶段，以及为什么每个阶段有不同的瓶颈（计算受限 vs 内存受限）
- 实现连续批处理和 PagedAttention 概念，以在并发请求下最大化 GPU 利用率
- 比较推理优化技术（KV 缓存、推测解码、Flash 注意力）及其吞吐量/延迟权衡

## 问题背景

你在 4xA100 GPU 上部署 Llama 3 70B。单个用户获得约 50 Token/秒。感觉快。然后 100 个用户同时访问端点。吞吐量降至 3 Token/秒/用户。你每月 $25,000 的 GPU 账单以比人类打字还慢的速度提供响应。

模型本身在 1 个用户和 100 个用户之间没有变化。相同的权重、相同的架构、相同的数学。变化的是你如何调度工作。朴素推理浪费了 90%+ 的可用 GPU 计算。等待第 47 个 Token 的用户在等待期间保持整个批处理槽位开放，而 GPU 内存总线在矩阵乘法之间空闲。与此同时，新用户的 2,000 Token 提示可以在此期间用有用的计算填满。

这不是扩展问题。这是调度问题。本课程的技术——KV 缓存、连续批处理、PagedAttention、推测解码、前缀缓存——是将每月 $25,000 推理账单与每月 $5,000 服务相同流量分开的东西。

通过连续批处理和 PagedAttention，vLLM 在 4xA100-80GB 上提供 Llama 3 70B，在低并发时实现约 50 Token/秒/用户，在 100 个并发请求时维持 15-25 TPS/用户。没有这些优化，相同硬件在该并发下仅提供 5 TPS/用户。相同的 GPU，相同的模型，4 倍吞吐量。

## 概念讲解

### 预填充 vs 解码

每个 LLM 推理请求有两个不同的阶段。

**预填充**处理整个输入提示。所有 Token 都已知，因此注意力可以跨完整序列并行计算。这是一个大型矩阵乘法——GPU 核心保持忙碌。瓶颈是计算：硬件每秒能交付多少 FLOP。一块 A100 执行 312 TFLOPS（BF16）。70B 模型上 4,096 个 Token 提示的预填充在单块 A100 上约需 400 毫秒。

**解码**逐个生成输出 Token。每个新 Token 关注所有先前的 Token，但每次前向传递只产生一个 Token。权重矩阵与预填充期间相同大小，但你用单个向量而非矩阵相乘。GPU 核心在微秒内完成，然后等待下一批权重从内存到达。瓶颈是内存带宽：你能以多快的速度将模型权重从 HBM 流式传输到计算单元。一块 A100 有 2 TB/s 带宽。FP16 中的 70B 模型是 140 GB。完整读取一次模型需 70 毫秒——这是单步解码的极限。

**每字节操作比**（也称为算术强度）捕获这种权衡。它衡量每从内存加载一个字节执行多少操作。

```
每字节操作比 = 每 Token FLOPs / 从内存读取的字节数
```

在批处理大小为 4,096 的预填充期间，你每次加载权重执行约 4,096 次乘加操作。比例高——你是计算受限。在批处理大小为 1 的解码期间，你每次加载权重执行约 1 次操作。比例低——你是内存受限。

基本洞察：*解码是内存受限的，因为你读取整个模型来生成单个 Token*。下面的每个优化要么减少你读取的内容，要么增加每次读取处理的 Token 批处理，要么完全避免读取。

### KV 缓存

在注意力期间，每个 Token 的查询关注每个先前 Token 的键和值向量。没有缓存，生成 Token N 需要为所有 N-1 个先前 Token 重新计算键和值投影。在生成 Token 2 时投射 Token 1，然后在生成 Token 3 时再次投射 Token 1，在生成 Token 4 时再次投射 Token 1。到 Token 1,000 时，你已经总共投射 Token 1 达 999 次。

KV 缓存存储来自所有先前 Token 的键和值投影。在生成 Token N 时，你只为 Token N 计算键和值，然后将它们与来自 Token 1 到 N-1 的缓存 K/V 连接起来。

**KV 缓存内存公式：**

```
KV 缓存大小 = 2 * 层数 * KV 头数 * 头维度 * 序列长度 * 每参数字节数
```

对于 Llama 3 70B（80 层，8 个 KV 头带 GQA，头维度=128，BF16）：

```
每 Token：2 * 80 * 8 * 128 * 2 字节 = 327,680 字节 = 320 KB
在 4,096 Token：320 KB * 4,096 = 1.28 GB
在 128K Token：320 KB * 131,072 = 40 GB
```

Llama 3 70B 的单个 128K 上下文对话消耗 40 GB KV 缓存——半块 A100 的内存。100 个并发用户各 4K Token，仅 KV 缓存就需要 128 GB。这就是 KV 缓存管理是推理优化核心挑战的原因。

### 连续批处理

静态批处理等待 N 个请求的批处理到达，一起处理它们，并等待*所有*完成才接受新请求。如果一个请求需要 500 个 Token 而另一个需要 10 个，短请求在完成后空闲 490 个解码步骤。

连续批处理（也称为迭代级批处理）在任何请求完成时立即将新请求插入批处理。批处理在每个解码步骤重新评估。10 个 Token 后完成的请求立即被等待请求替换。

吞吐量改进取决于输出长度变化多少。长度均匀时，连续批处理与静态批处理匹配。长度变化（常见情况）时，连续批处理可以提供 2-5 倍更高吞吐量，因为 GPU 槽位永远不会空闲。

### PagedAttention

每个请求的 KV 缓存是连续的内存块。当请求到达和离开时，内存碎片化——就像操作系统中的 RAM 碎片化。4K Token 请求需要 1.28 GB 连续空间。即使你有总共 2 GB 空闲，你可能没有 1.28 GB *连续*。你要么浪费内存，要么拒绝请求。

PagedAttention（来自 vLLM）将操作系统风格的虚拟内存应用于 KV 缓存。不是为每个请求分配一个连续块，而是分配固定大小的"页面"（通常每个 16 个 Token）。页面可以在 GPU 内存的任何地方。页表将每个请求的逻辑序列位置映射到物理页面位置。

PagedAttention 还启用共享前缀的**写时复制**。如果 50 个请求共享相同的系统提示，该系统提示的 KV 缓存页面只存储一次，被全部 50 个请求引用。只有请求分叉（不同用户消息）时，它才获得自己的页面。这对共享系统提示的应用程序大幅降低内存使用。

vLLM 报告通过 PagedAttention 接近零内存浪费（约 4% vs 朴素分配中的约 60-80%）。

### 推测解码

解码很慢，因为它是顺序的——你生成一个 Token，反馈它，生成下一个。但如果你能以便宜的方式猜测接下来的 5 个 Token，然后一次性验证它们呢？

推测解码使用一个小的、快速的**草稿模型**生成 K 个候选 Token。大型**目标模型**然后在单次前向传递中处理所有 K 个候选（看起来像预填充——并行、计算受限、高效）。如果目标模型同意草稿模型的预测，你在一次目标前向传递的时间内接受全部 K 个 Token。如果它在位置 j 不同意，你接受 Token 1 到 j-1 并丢弃其余。

速度取决于**接受率**——草稿模型预测与目标匹配的频率。对于为 Llama 3 70B 起草的 Llama 3 8B，自然语言的接受率通常为 70-85%。这转化为 2-3 倍解码加速。

三种推测解码方法：

| 方法 | 草稿来源 | 接受率 | 开销 |
|------|---------|--------|------|
| 草稿-目标（Leviathan 等人） | 单独小模型 | 70-85% | 草稿模型内存 |
| EAGLE（Li 等人） | 目标上的轻量级头 | 75-90% | 约 1% 额外参数 |
| N-gram 查找 | Token n-gram 表 | 40-60% | 可忽略 |

**EAGLE** 在目标模型的隐藏状态顶部训练一个小的自回归头。它使用目标模型倒数第二层的特征预测下一个 Token 的嵌入。因为它操作在目标模型自己的表示上（而非单独模型的表示），它以最小额外内存实现更高接受率。EAGLE-2 添加动态草稿树，根据上下文调整候选数量。

**N-gram 推测解码**维护来自当前上下文或预构建语料库的 n-gram 续表。如果草稿匹配同一会话中之前出现的内容（重复模式、代码、结构化输出），它以零神经网络开销触发。平均接受率较低，但每次推测的成本基本为零。

推测解码是*数学上精确的*——输出分布与目标模型的分布相同。它不是近似。验证步骤确保每个接受的 Token 具有目标模型本应分配的完全相同的概率。

### 前缀缓存

许多请求共享相同的前缀。聊天机器人系统提示。RAG 上下文块。少样本示例集。没有前缀缓存，每个请求从头开始重新计算这些共享 Token 的 KV 缓存。

前缀缓存存储常见前缀的 KV 缓存并在请求间重用。当带有已知前缀的新请求到达时，系统复制（或引用）缓存的 KV 条目，仅计算唯一后缀的 KV。

对于所有请求共享的 2,000 Token 系统提示，前缀缓存每请求消除约 400 毫秒预填充。在 100 请求/秒时，每秒节省 40 秒 GPU 计算——超过一块 GPU 的工作量。

SGLang 的 RadixAttention 用基数树（字典树）实现前缀缓存，按 Token 内容索引前缀。任何匹配存储前缀的请求免费获得其 KV 缓存。树启用部分前缀匹配——如果你与缓存条目共享 2,000 前缀 Token 中的 1,500 个，你重用那 1,500 并仅重新计算 500。

### 推理引擎

三个引擎主导生产 LLM 服务：

| 引擎 | 关键创新 | 最适合 |
|------|---------|--------|
| vLLM | PagedAttention、连续批处理 | 通用服务，最高兼容性 |
| SGLang | RadixAttention（前缀缓存）、结构化生成 | 多轮聊天机器人、受限解码 |
| TensorRT-LLM | NVIDIA 内核融合、FP8 量化 | NVIDIA 硬件上的最大单 GPU 吞吐量 |

**vLLM** 是默认起点。它支持最广泛的模型范围，在任何 GPU 供应商（NVIDIA、AMD、Intel）上运行，并通过 PagedAttention + 连续批处理实现强大吞吐量。OpenAI 兼容 API 意味着你可以将其作为任何 OpenAI API 调用的替代品。

**SGLang** 建立在 vLLM 基础上，但添加 RadixAttention 用于前缀缓存和结构化 LLM 程序的 DSL。如果你的工作负载涉及多轮对话、工具使用或受限解码（JSON 输出、正则表达式引导生成），SGLang 通常通过前缀重用比 vLLM 快 2-5 倍。

**TensorRT-LLM** 将模型编译为优化的 NVIDIA GPU 内核。它融合操作（注意力 + 线性 + 激活在一个内核中），在 H100 GPU 上使用 FP8，并与 NVIDIA Triton 推理服务器集成用于生产部署。它在 NVIDIA 硬件上实现最高的单 GPU 吞吐量，但需要更多设置且仅在 NVIDIA GPU 上工作。

Llama 3 70B 的真实数字（4xA100-80GB，BF16）：

| 指标 | vLLM | SGLang | TensorRT-LLM |
|------|------|--------|---------------|
| 吞吐量（1 用户） | 约 50 TPS | 约 55 TPS | 约 65 TPS |
| 吞吐量（100 用户） | 约 2,500 总 TPS | 约 3,200 总 TPS | 约 3,000 总 TPS |
| 首个 Token 时间 | 约 400 毫秒 | 约 300 毫秒（前缀命中） | 约 350 毫秒 |
| 最大上下文 | 128K | 128K | 128K |

### 每字节操作框架

你无法优化你不测量的东西。每字节操作比告诉你是在计算受限还是内存受限，这决定了哪些优化重要。

```
计算上限：GPU 的峰值 FLOPS
内存上限：峰值带宽 * 每字节操作比
```

当每字节操作比低（解码、小批处理）时，你达到内存带宽上限。添加更多计算（更高时钟、更多核心）没有帮助。你需要减少内存读取（量化、KV 缓存压缩）或增加批处理大小以将读取分摊到更多有用工作上。

当每字节操作比高（预填充、大批处理）时，你达到计算上限。内存带宽优化没有帮助。你需要更快的 GPU、内核融合或减少精度以挤出更多 FLOPS。

| 场景 | 每字节操作比 | 受限 | 优化方式 |
|------|------------|------|---------|
| 预填充，批处理=1 | 约 4,096 | 计算 | 内核融合、FP8 |
| 解码，批处理=1 | 约 1 | 内存 | 量化、KV 压缩 |
| 解码，批处理=32 | 约 32 | 内存 | 更大批处理、连续批处理 |
| 解码，批处理=256 | 约 256 | 过渡 | 两者都重要 |
| 解码，批处理=1024 | 约 1,024 | 计算 | 内核融合、张量并行 |

A100 上的交叉点大约在每字节操作比 = 156（312 TFLOPS / 2 TB/s）。低于 156，你是内存受限。高于 156，你是计算受限。连续批处理通过每迭代打包更多 Token 将解码推向这个交叉点。

使用 vLLM：

```python
from vllm import LLM, SamplingParams

llm = LLM(
    model="meta-llama/Llama-3-70B-Instruct",
    tensor_parallel_size=4,
    enable_prefix_caching=True,
    max_model_len=8192,
    gpu_memory_utilization=0.9,

```

使用 SGLang 进行前缀缓存 + 结构化输出：

```python
import sglang as sgl

@sgl.function
def classify(s, text):
    s += sgl.system("你是一个分类器。仅输出 JSON。")
    s += sgl.user(f"分类这段文本：{text}")
    s += sgl.assistant(sgl.gen("result", regex=r'\{"label": "(positive|negative|neutral)"\}'))

runtime = sgl.Runtime(model_path="meta-llama/Llama-3-70B-Instruct", tp_size=4)
sgl.set_default_backend(runtime)

results = classify.run_batch([
    {"text": "这个产品太棒了！"},
    {"text": "糟糕的体验。"},
    {"text": "还行吧。"},
])
```

## 练习题

1. 修改 KV 缓存分析器以比较 FP16 vs FP8 vs INT4 KV 缓存量化。对于 4K 上下文的 Llama 3 70B，计算 4xA100-80GB 上每个的最大并发用户数。INT4 的 KV 缓存应该大致将用户容量增加 4 倍。

2. 扩展连续批处理模拟器以跟踪 GPU 利用率（每步填充的批处理槽位比例）。为输出长度遵循帕累托分布（shape=1.5，scale=20）的 50 个请求绘制随时间变化的利用率。连续批处理应保持 >80% 利用率。

3. 实现分组查询注意力（GQA）版本的 KV 缓存，其中 `num_kv_heads < num_query_heads`。Llama 3 70B 使用 64 个查询头但只有 8 个 KV 头。计算与完整多头注意力相比的内存节省（KV 缓存大小减少 8 倍）。

4. 构建使用 LRU 驱逐的前缀缓存。设置 max_entries 为 500 并生成 1,000 个请求，其中 60% 共享 5 个常见前缀之一。测量命中率并与无限缓存比较。通过良好的驱逐，命中率应保持在 55% 以上。

5. 扩展推测解码模拟器以实现基于树的推测（EAGLE-2 风格）。不是单个 K 个草稿 Token 链，而是在每个深度生成一个候选树（例如，3 级每级 2 个分支 = 8 个叶候选）。与线性推测相比，每验证轮次接受的总 Token 数。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| 预填充 | "处理提示" | 并行计算所有输入 Token 的注意力——计算受限，因为完整矩阵乘法保持 GPU 核心忙碌 |
| 解码 | "生成 Token" | 每次前向传递产生一个 Token，每次读取完整模型权重——内存受限，因为计算在下一批权重到达前完成 |
| KV 缓存 | "缓存注意力状态" | 存储所有先前 Token 的键和值投影，使它们在每次解码步骤中无需重新计算——用内存换计算 |
| 连续批处理 | "动态批处理" | 在任何请求完成时立即将新请求插入运行批处理，每解码迭代评估而非等待整批完成 |
| PagedAttention | "KV 缓存的虚拟内存" | 在固定大小页面而非连续块中分配 KV 缓存，消除内存碎片化并为共享前缀启用写时复制 |
| 推测解码 | "草稿和验证" | 使用快速草稿模型提议多个 Token，然后在单次目标模型前向传递中全部验证——数学上精确，2-3 倍加速 |
| EAGLE | "自推测解码" | 一种推测解码变体，在目标模型自己的隐藏状态上训练轻量级头，实现比单独草稿模型更高的接受率 |
| 前缀缓存 | "重用系统提示 KV" | 为常见前缀（系统提示、少样本示例）存储计算的 KV 缓存条目并在请求间重用，跳过冗余预填充 |
| 每字节操作比 | "算术强度" | 计算操作与内存字节读取的比率——决定工作负载是计算受限（高比率）还是内存受限（低比率） |
| 首个 Token 时间 | "TTFT" | 从接收请求到产生第一个输出 Token 的延迟——由长提示的预填充时间主导 |

- Leviathan 等人，"Fast Inference from Transformers via Speculative Decoding" (2023) —— 基础论文证明草稿-验证推测在实现 2-3 倍加速的同时产生精确的目标模型分布
- Li 等人，"EAGLE: Speculative Sampling Requires Rethinking Feature Uncertainty" (2024) —— 通过在目标模型自己的特征而非单独模型上训练头来实现更高接受率
- Zheng 等人，"SGLang: Efficient Execution of Structured Language Model Programs" (2024) —— 引入用于前缀缓存的 RadixAttention 和多调用 LLM 程序编程模型
- Williams 等人，"Roofline: An Insightful Visual Performance Model for Multicore Architectures" (2009) —— 将每字节操作框架形式化的原始屋顶线论文，用于推理计算与内存瓶颈
