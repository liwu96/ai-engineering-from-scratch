# 构建完整的 LLM 管道

> 第01到12课的所有内容只是管道的一个阶段。本课程是将这些阶段转变为单个端到端运行的脚手架：分词、预训练、扩展、SFT、对齐、评估、量化、服务。你不会在笔记本电脑上训练 70B 模型。你将产生编排层、清单、评估门控和回滚计划，2026 年前沿团队用来决定什么可以发布。这是顶点。

**类型:** 构建
**语言:** Python (stdlib)
**前置要求:** 第10阶段所有课程 01-12
**时间:** ~120分钟

## 学习目标

- 将十一门先前课程（分词器、数据、预训练、扩展、SFT、RLHF、DPO、CAI、评估、量化、推理）组成单个可复现管道规范
- 定义阶段之间的工件契约：每个阶段消耗什么、产生什么，以及下一阶段如何验证输入
- 构建编排器，跟踪实验、哈希工件，并根据评估阈值门控发布决策
- 设计回滚计划：哪些工件便宜可重新运行，哪些昂贵，损坏的检查点成本几何

## 问题背景

先前的课程各自有效。分词器训练了。微型 GPT 预训练了。SFT 数据集组装了。奖励模型训练了。DPO 运行了。评估测量了。量化权重导出了。推理服务器启动了。每个都是笔记本。每个都有自己的约定、自己的输出路径、自己的种子。

前沿训练运行不是笔记本。Llama 3 405B 在大约 54 天内消耗了 3000 万 H100 小时。DeepSeek-V3 使用了约 280 万 H800 小时。在此期间，一个损坏的检查点、一个数据污染、一个评估退化可能让团队损失一周实时时间和一个月 GPU 预算。团队生存的方式是通过管道卫生：每个阶段有确定性输入、确定性输出、清单、哈希和门控。

这是顶点。你不会在笔记本电脑上端到端运行管道。你将编写协调阶段的编排器、描述运行的清单、门控发布决策的验证器和让第三方从单个文件重新运行你工作的重播计划。代码小；纪律大。

该模式从 1 亿到 1 万亿参数不变。相同的四个组件——清单、编排器、评估门控、工件存储——运行 Llama 3 也运行你的爱好 GPT。区别是每个阶段配置中的数字大小，而非管道形状。

## 概念讲解

### 十二个阶段

每门第10阶段课程都是一个阶段。这是完整的依赖图。

阶段 07 和 08 可以并行运行。其他都是硬依赖。阶段 02（分词器）的更改使每个下游工件失效。阶段 10（评估）的更改仅使发布决策失效。

### 清单

清单是一个描述运行完全足够的单个文件，可以重播它。管道产生的任何东西都不应依赖于不在清单中的状态。字段是强制性的无聊。

```
pipeline_version: 1.2.3
seed: 42
git_commit: a1b2c3d4
stages:
  01_tokenizer:
    recipe: bpe_32k
    input_hash: sha256:...
    output_hash: sha256:...
    wall_clock_sec: 3600
    cost_usd: 12
```

阶段 N 的输出哈希是阶段 N+1 的输入哈希。任何偏差，管道停止。这是你及早发现数据损坏的方式。这也是不同大陆的队友验证他们重播是否产生与你相同工件的方式。

在实践中，团队使用小型 YAML 模式加清单检查器，与先前成功运行进行差异比较。预期字段之外的任何增量（成本、墙钟）都是危险信号。

### 工件类型

每个阶段的输出是类型化工件。不是目录 blob，不是 pickle，而是具有已知模式的命名类型。

| 阶段 | 工件类型 | 关键字段 |
|-------|--------------|-----------|
| 01-02 | 分词器 | vocab.json、merges.txt、config.json、哈希 |
| 03 | 数据集 | 分片[]、行数、Token 数、去重统计 |
| 04-05 | 检查点 | weights.safetensors、config.json、优化器状态、步数 |
| 06 | SFT 模型 | 检查点 + SFT 配方 + 数据混合 |
| 07 | 奖励模型 | RM 检查点 + 偏好数据哈希 |
| 08-09 | 策略 | 检查点 + 参考哈希 + beta + 消耗 KL 预算 |
| 10 | 评估报告 | 基准分数 + 回归差异 + 评估数据哈希 |
| 11 | 量化模型 | 量化权重 + 校准数据 + 与 FP16 的准确性差异 |
| 12 | 服务器规范 | 端点 + 模型哈希 + 配置 + 可观测性钩子 |

类型防止最常见的失败模式：使用阶段 08 输出作为阶段 06 输入，通过 SFT 路径发布 DPO 训练模型。类型化工件和类型化阶段签名使这些错误成为编译时失败，而非第五天失败。

### 评估门控

发布不是"训练完成"。发布是"训练完成且评估门控通过"。门控在运行开始前定义。

```
gates:
  mmlu:      >= 基线 + 0.5   # 无回归
  humaneval: >= 基线 + 1.0
  truthfulqa: >= 基线         # 无下降
  safety_refusal_rate: <= 0.05
  kl_from_reference: <= 25.0
  cost_total_usd: <= 50000
```

每个门控都是数字阈值。没有"看起来不错"的门控。没有主观签字。如果每个门控都通过，工件被标记为可发布。如果任何门控失败，运行被暂停，等待显式覆盖（本身记录在清单中）。

两个门控捕获大多数灾难。*回归*门控（新模型必须在核心基准上至少与先前一样好）捕获训练错误。*KL 预算*门控（对齐策略与参考的漂移不能超过 X）捕获对齐过度烹饪。每个生产管道都有两者。

### 编排器

一小段代码，读取清单、分派阶段、跟踪工件，并在任何合同违规时停止。这不是 Airflow。这不是 Kubeflow。对于管道卫生，你想要自己写的无聊东西。

编排器的工作很窄：

1. 从清单解析 DAG。
2. 对于每个阶段，检查预期输出是否已存在于正确哈希（如果是则跳过）。
3. 运行阶段，捕获 stdout/stderr，测量墙钟和成本。
4. 根据下游阶段的预期输入哈希验证输出哈希。
5. 失败时，写入包含确切失败阶段的部分清单并以非零退出。

那是 200 行 Python。它看起来像本课程 `code/main.py` 中的文件。在底层，真实管道使用 `torchrun` 或 `ray` 在集群上执行各个阶段，但编排器本身在单个机器上运行。

### 实验跟踪和工件存储

两个外部系统锚定管道。

**实验跟踪器（wandb、neptune、mlflow）。** 记录每阶段的损失曲线、评估指标、系统遥测。跟踪器是你三周后需要比较运行 A 与运行 B 时去的地方。团队几乎总是为此使用托管跟踪器——自己写会浪费应该用于训练的时间。

**工件存储（S3、R2、GCS）。** 检查点、数据集、分词器、评估报告的不可变对象存储。工件通过哈希而非文件名寻址。像 `latest.pt` 这样的文件名是致命陷阱；`ckpt-7b-step-20000-sha256:abc123.safetensors` 是合同。

编排器写入两者。跟踪器是给人类看图表的。工件存储是给下一阶段查找输入的。

### 成本计算

前沿运行附有美元数字。预算纪律发生在两个地方。

**运行前估算。** 从清单计算预期 FLOPs（预训练：6 x 参数 x Token），预期 GPU 小时（FLOPs / 峰值吞吐量 / 利用率），以及当前租赁费率下的美元成本。如果估算超过预算门控，管道拒绝启动。

**运行中跟踪。** 每阶段的墙钟和成本记录到清单。每阶段后检查剩余预算。如果阶段超支，用新的剩余预算评估下一阶段。你不会在 VC 打电话时发现没钱了。

Llama 3 的报告成本是 $61M。DeepSeek-V3 报告主预训练运行 $5.6M。比率主要是硬件效率加混合专家——但具体成本是可见的，因为两个团队都按阶段而非按运行跟踪。

### 可复现性 vs 确定性

这些不同。*可复现*意味着相同清单加相同代码加相同基础架构在下游指标上产生具有等价性的检查点。*确定性*意味着位级相同输出。

现代 LLM 训练是可复现但非确定性的。分布式训练的归约顺序、GPU 内核非确定性（cuBLAS、flash-attn）和混合精度舍入结合产生运行间在 1e-5 级别不同的浮点数。这对最终指标没问题，它们不会移动。如果你试图用位级差异调试，这是致命的。治疗是记录每阶段的输入哈希、输出哈希和标题指标——如果这些匹配，运行就是"复现"的，即使权重不是位级相同。

### 回滚计划

在运行开始前，写下每阶段失败时发生什么。三个类别。

- **便宜可重新运行**（小时）：分词器、评估、量化、推理服务器。只需重新运行。
- **中等**（天）：SFT、DPO、CAI。保留基础模型；仅重新运行对齐阶段。
- **昂贵**（周和百万美元）：预训练。这里的回滚计划不是"重新运行"。而是"使用上一个好的检查点，用修订的输入重新运行更便宜的下游阶段"。

因为阶段依赖是类型化和哈希化的，编排器可以自动计算回滚集：使失败阶段及其每个后代失效。阶段 06（SFT）的失败使 06、07、08、09、10、11、12 失效。阶段 11（量化）的失败仅使 11 和 12 失效。预先命名这个避免在凌晨 4 点团队筋疲力尽时即兴发挥。

### 2026 年观察到的生产配方

大多数前沿团队收敛于相同的骨架。

- 分词器：128k BPE 带字节回退。在小型平衡多语言切片上训练。
- 预训练：10-20T Token，主要是网页加代码加合成。Muon 或 AdamW 优化器。FSDP2 或 DeepSpeed ZeRO-3。梯度检查点。BF16 权重，FP32 主。
- SFT：500k-2M 指令对，混合人类和合成，严格去重与评估集。
- 对齐：DPO 或 CAI + GRPO。仅在对齐信号对 DPO 来说太多维时使用 RLHF。
- 评估：MMLU-Pro、MATH、HumanEval+、GPQA、SWE-Bench Verified、LiveBench，加上公众从未见过的私人留出集。
- 量化：4 位 GPTQ 或 AWQ 用于服务，8 位用于准确性差异重要的安全评估。
- 服务：vLLM、TensorRT-LLM 或内部。连续批处理。推测解码。KV 缓存驱逐。

数字每六个月变化。骨架不变。

## 动手实践

本课程的代码是编排器和清单检查器，而非十二个训练脚本。每个阶段用占位符模拟，产生具有正确形状和哈希的输出工件。端到端运行编排器证明管道 plumbing 在你烧钱在真实阶段上之前工作。

见 `code/main.py` 获取完整实现。关键部分：

- `Manifest` 数据类：管道版本、种子、git 提交、阶段、门控。
- `Stage` 数据类：名称、类型、输入（哈希）、输出（哈希）、墙钟、成本。
- `Orchestrator.run()`：解析 DAG、分派阶段、验证哈希、更新清单。
- `EvalGate.check()`：读取阈值、与最新评估报告比较、返回通过/失败。
- `ArtifactStore`（内存存根）：按哈希 put/get，模拟 S3。
- `CostTracker`：每阶段和累计，超出上限时停止。

`main.py` 中的管道运行十二个占位阶段，产生清单，并练习失败的评估门控以展示暂停运行的样子。将每个占位符替换为相应课程的真实训练脚本，你就有了真实前沿管道使用的骨架。

## 使用实践

典型工作流有三个命令。

```
python code/main.py plan    # 验证清单、计算成本估算、打印 DAG
python code/main.py run     # 执行阶段，写入 manifest.out.yaml
python code/main.py gate    # 读取 manifest.out.yaml、应用评估门控、发布或暂停
```

每次先运行 `plan`。大多数管道 bug 在计划时暴露——缺失门控阈值、过时哈希、预算超支。运行 `plan` 是免费的。运行 `run` 是昂贵的。通过在便宜侧捕获 bug 来省钱。

`gate` 的输出要么是 `SHIP` 要么是 `HOLD: <原因>`。暂停运行不是失败；而是决策点。指定审查员要么覆盖（覆盖本身被记录），要么批准回滚。

## 产出成果

本课程产出 `outputs/skill-llm-pipeline-reviewer.md`。向它提供提议的管道清单，它检查所有合同：阶段类型、哈希链、门控、回滚计划、成本估算。它拒绝批准缺失评估门控、无界 KL 预算或混合评估和训练数据的清单。

## 练习题

1. 扩展编排器以支持阶段 07 和 08 的并行执行。使用 stdlib `concurrent.futures` 模块。确认最终清单记录两个阶段的输出，且阶段 09 的输入哈希是两者的确定性组合。

2. 添加"污染检查"门控。给定评估数据集哈希和训练数据集分片，计算重叠（精确字符串匹配或 13-gram 匹配）。如果重叠超过 0.1%，门控失败。用污染训练集喂它并确认门控暂停运行。

3. 从头开始实现成本估算器。对于阶段 04（预训练），将 FLOPs 估算为 6 x 参数 x Token，假设在 H100 989 TFLOPS BF16 上 40% MFU（模型 FLOPs 利用率），每小时 $2.50。报告在 2T Token 上训练的 7B 模型的估算。与发布的 Llama 2 数字比较。

4. 构建部分回滚。模拟阶段 09（CAI）的失败，然后重新运行阶段 09 到 12，同时保留 01-08 缓存。编排器应该通过哈希检测缓存工件并跳过它们。测量与完全重新运行相比节省的墙钟时间。

5. 添加可观测性。为每个阶段发出 OpenTelemetry span，属性为参数、看到的 Token、损失和成本。将 span 管道到本地收集器。重点不是仪表板；重点是每个阶段的健康状况可从单个跟踪 ID 追踪。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| 清单 | "配方文件" | YAML 或 JSON 描述管道版本、种子、每阶段配置和门控阈值——足以重播运行 |
| 内容寻址 | "按哈希而非名称" | 工件通过其内容的 SHA-256 存储，所以你永远不会混淆版本 A 和版本 B |
| 评估门控 | "发布标准" | 基准指标和安全分数上的数字阈值，必须通过工件才能被标记为可发布 |
| KL 预算 | "对齐漂移多远" | 跨对齐阶段累积 KL（策略 || 参考）的上限，作为门控执行 |
| MFU | "GPU 用了多少" | 模型 FLOPs 利用率——实现 FLOPs 除以理论峰值。70B 规模 40% 典型，7B 规模 55% |
| 回滚计划 | "坏了怎么办" | 每阶段失败时预写的行动集：重新运行、回退、用修订输入重新训练 |
| 编排器 | "指挥" | 读取清单、分派阶段、验证哈希、在任何合同违规时暂停的进程 |
| 工件存储 | "权重的版本化 S3" | 不可变内容寻址对象存储——检查点、数据集、评估报告的单一真相来源 |
| 可复现 | "重播时相同指标" | 不同位级权重但等价的下游指标——分布式 LLM 训练的现实目标 |
| 成本门控 | "不能超过 X" | 预运行成本估算加运行中跟踪——如果估算超过预算，管道拒绝启动 |
