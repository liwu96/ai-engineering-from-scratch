# 检查点和回滚

> 每个图状态转换都持久。工作器崩溃时，其租约过期，另一个工作器在最新检查点恢复。Cloudflare Durable Objects在数小时或数周内保持状态。提议-然后-提交（第15课）定义每动作的回滚计划。执行后验证闭合循环。EU AI法案第14条使高风险系统的有效人类监督成为强制——实践中这意味着检查点必须可查询、回滚必须预演、审计跟踪必须存活部署。尖锐故障模式：没有幂等键和前提条件检查，瞬态失败后的重试可以双倍执行已批准的动作。执行后验证是捕获它的方法。

**类型:** 学习
**语言:** Python (stdlib, 检查点和回滚状态机)
**前置要求:** 第15阶段 · 12 (持久执行), 第15阶段 · 15 (提议-然后-提交)
**时间:** ~60分钟

## 问题背景

持久执行（第12课）使崩溃的智能体可恢复。提议-然后-提交（第15课）使已批准的动作可审计。本课将它们结合：当已批准的动作部分执行、崩溃、恢复时发生什么？回滚何时运行，针对什么状态？

真实系统以不同方式连接：

- **LangGraph** 将每个图状态转换检查点到PostgreSQL。工作器崩溃时，租约释放，另一个工作器在最新检查点恢复。`interrupt()` 上的工作流暂停本身持久。
- **Cloudflare Durable Objects** 在数小时或数周内保持每键状态。将计算与批准动作的存储共同定位。
- **微软智能体框架** 在工作流API中公开 `Checkpoint` 原语；重放加幂等覆盖重试。

在每种情况下，实际有效的组合是：幂等键（防止双倍执行）+ 前提条件检查（状态仍与批准时一致）+ 执行后验证（副作用实际发生）+ 验证失败时回滚。

## 概念讲解

### 每个转换都持久

图状态转换是工作流从一个命名状态移动到另一个命名状态的任何步骤。天真实现仅在特定提交点持久；生产实现持久每个转换。成本（几次额外写入）相对于可靠性增益（重放在任何地方着陆，租约恢复精确）很小。

### 租约恢复

工作器崩溃时，工作流不丢失；租约（此工作器执行此运行的短期声明）仅过期。另一个工作器接收最新检查点并恢复。租约机制使生产系统能够在不丢失进行中的工作的情况下存活滚动部署。

### 幂等加前提条件

仅有幂等不够。考虑：工作流被批准在"余额>$1000时从A转账$100到B"。工作流已提交、执行中崩溃、恢复。如果仅检查幂等键且执行恢复，转账运行一次（正确）。但考虑崩溃和恢复之间，A的余额通过不同工作流降至$500。幂等检查仍通过；前提条件不通过。没有前提条件检查，我们交付透支。

每个有实际影响的动作需要两者：

- **幂等键**：防止双倍执行。
- **前提条件检查**：确认状态仍与批准时一致。

### 执行后验证

"工具返回200"不是验证。真实验证重新读取目标状态并确认副作用实际发生。模式：

- 数据库更新：`UPDATE ... RETURNING *` 然后断言返回的行匹配预期状态。
- 邮件发送：提交后检查已发送文件夹中的消息ID。
- 文件写入：读回文件并哈希。
- API调用：目标资源的后续 `GET`。

如果验证失败，工作流处于已知不良状态。回滚启动。

### 回滚计划

提议-然后-提交（第15课）中的每个有实际影响的动作携带回滚计划。类型：

- **带内回滚**：直接反转副作用（`INSERT` 后 `DELETE`、`Send-correction-email` 后发送）。
- **补偿事务**：中和原始的新动作（标准SAGA模式）。
- **带外回滚**：提醒人类、暂停工作流、留下不良状态供调查。

空操作回滚（"我们无法撤销此"）必须在提议中命名。无回滚的动作在提交时需要更强的HITL（第15课挑战-响应）。

### EU AI法案第14条操作解读

第14条要求高风险系统的"有效人类监督"。操作术语，实施者将其解读为：

- 检查点可被审计员查询。
- 回滚已预演（至少端到端测试一次）。
- 审计跟踪存活部署（检查点后端非短暂）。
- 失败的验证被警报，非静默记录。

崩溃中提交、恢复、完成副作用而无验证+回滚路径的工作流不通过第14条测试。

### 尖锐故障模式：双倍执行

此空间最常见的生产事件：

1. 动作已批准，幂等键k。
2. 提交开始、执行、返回200。
3. 工作流在持久化"已提交"状态前崩溃。
4. 工作流恢复；看到"已批准但未提交"；重新执行。
5. 副作用触发两次。

缓解：执行前持久"进行中"意图，用幂等键执行，然后仅在执行后验证成功后标记"已提交"。如果动作触发且状态写入失败，你知道要验证和（如有必要）重新触发。如果状态写入成功且动作失败，你通过恢复路径验证并恰好触发一次。

`code/main.py` 实现带幂等、前提条件、验证和回滚的检查点工作流。驱动程序模拟四种场景：干净运行、崩溃后重试（幂等捕获）、前提条件失败（工作流中止而不触发）、验证失败（回滚触发）。

## 练习题

1. 运行 `code/main.py`。验证四种场景。对于提交期间崩溃的情况，确认动作在重试中恰好触发一次。

2. 修改"先标记完成，再做"模式，使状态写入在动作后触发。重新运行崩溃场景。测量触发多少重复动作。

3. 为特定生产动作（例如"发布到Slack频道"）设计回滚计划。分类为带内、补偿或带外。证明选择。

4. 取你了解的一个工作流。识别每个状态转换。用持久性要求标记每个（持久/不持久）。计数当前未持久的转换。

5. 预演回滚测试：设计端到端测试，运行真实工作流、崩溃它、确认回滚路径触发。测试断言什么？

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|---|---|---|
| 检查点 | "保存点" | 每个图状态转换持久到持久存储 |
| 租约 | "工作器声明" | 工作器执行运行的短期声明；崩溃时过期 |
| 前提条件 | "状态门" | 断言状态仍与批准动作一致 |
| 执行后验证 | "重新读取检查" | 确认副作用实际发生在目标系统中 |
| 带内回滚 | "直接撤销" | 用逆操作反转副作用 |
| 补偿事务 | "SAGA撤销" | 中和原始的新动作 |
| 先标记完成 | "状态写入顺序" | 在从提交返回前持久已提交状态 |
| 第14条 | "EU AI法案人类监督" | 操作：可查询检查点、预演回滚、可审计跟踪 |
