# Claude Code作为自主智能体：权限模式和自动模式

> Claude Code暴露七种权限模式。"plan"在每次动作前询问，"default"仅询问风险动作，"acceptEdits"自动批准文件写入但仍确认shell执行，"bypassPermissions"批准一切。自动模式（2026年3月24日）用两阶段并行安全分类器替换每次动作批准：每动作运行单token快速检查；标记动作启动思维链深度审查。动作预算通过 `max_turns` 和 `max_budget_usd` 强制执行。自动模式作为研究预览发布——Anthropic明确声明分类器单独不足。

**类型:** 学习
**语言:** Python (stdlib, 两阶段分类器模拟器)
**前置要求:** 第15阶段 · 01 (长时程智能体), 第15阶段 · 09 (编码智能体全景)
**时间:** ~45分钟

## 问题背景

机器上的自主编码智能体是一个独特的安全类别。攻击面是智能体能触及的一切——文件系统、网络、凭证、剪贴板、任何浏览器标签、任何开放终端。Bruce Schneier等人公开标记了这一点：计算机使用智能体不是聊天机器人的"功能更新"，它们是一种具有新风险特征的新型工具。

Claude Code的权限系统是Anthropic的答案。不是"自主/非自主"一个开关，而是七个模式跨越能力阶梯：plan → default → acceptEdits → … → bypassPermissions。每个模式是每次动作审查与速度之间不同的权衡。自动模式（2026年3月）添加两阶段分类器，将分类器判断为安全的动作的批准移出用户关键路径，同时为标记动作保留审查层。

工程问题：该系统捕获什么、遗漏什么，给定任务实际保证哪个模式？

## 概念讲解

### 七种权限模式

| 模式 | 行为 | 何时使用 |
|---|---|---|
| `plan` | 智能体提出计划；用户批准整个计划；每次动作执行前审查 | 不熟悉任务；生产相邻代码；首次在仓库上使用智能体 |
| `default` | 智能体运行动作；对任何"风险"动作提示用户（shell执行、破坏性操作、网络调用） | 大多数交互编码会话 |
| `acceptEdits` | 文件写入自动批准；shell执行和网络调用仍提示 | 跨多文件重构遍次 |
| `acceptExec` | shell命令在策划允许列表内自动批准；写入自动批准 | 紧内循环，每个shell命令是 `npm test` 或类似 |
| `autoMode` | 两阶段安全分类器；标记动作提升到审查 | 约束工作空间中的长时程无人值守运行 |
| `yolo` | 跳过大多数提示；仍运行工具允许列表/拒绝列表 | 短暂沙箱、CI作业、研究脚本 |
| `bypassPermissions` | 批准一切 | 仅在愿意丢弃的短暂容器内记录 |

（上面的名称匹配公共Claude Code文档；"yolo"是宽松中间地带的非正式简写。）

### 自动模式一页

自动模式（2026年3月24日启动）是将每次动作批准委托给模型的首个权限模式。结构：

1. **阶段1 — 单token分类器。** 在每个提议动作上运行。便宜。返回"安全"或"标记"。设计为与主智能体循环并行运行，因此批准动作不在队列中等待。
2. **阶段2 — 二次策略/安全审查。** 仅在标记动作上运行。对动作、会话当前状态和声明任务执行聚焦的策略和安全评估。信心低时升级到用户HITL。

预算控制与分类器并列：

- `max_turns` — 会话总迭代次数。
- `max_budget_usd` — 中止会话的美元上限。
- 每工具动作计数限制（不超过N次 `WebFetch` 调用等）。

### 系统捕获什么

- 工具输入中映射到已知风险动作形状的直接提示注入。
- 重复工具循环——分类器可以看到动作N+1与动作N几乎相同，连续五次。
- 否则仅文件编辑会话上明显超出范围的shell命令。

### 系统可能遗漏什么

- **微妙提示注入** 调节行为而不产生单个标记动作。间接提示注入不是完全可修补的漏洞（OpenAI准备负责人，2025年，关于浏览器智能体——见第11课）。
- **语义级异常行为。** 每个单独动作可以看起来安全，而组合轨迹有害。分类器评判动作；它不重新推导用户意图。
- **通过合法渠道外泄。** 写入你拥有的文件，然后 `git push` 到公共仓库，是一系列允许动作的序列，其组合是问题。

### 研究预览框架

Anthropic将自动模式作为研究预览发布。文档明确分类器是层而非解决方案：用户预期将自动模式与预算、允许列表、隔离工作空间和轨迹审计（第12-16课）结合使用。预览框架也反映记录的评估与部署差距（第1课）——通过离线评估的分类器可以在真实会话中表现不同，其中用户上下文模糊。

### 该阶梯在工作流中的位置

- 不熟悉任务：从 `plan` 开始。阅读计划比回滚糟糕运行便宜。
- 已知重构：`acceptEdits` 节省大量确认点击。
- 无人值守后台运行：仅在爆炸半径已测量的工作空间内 `autoMode`（无凭证、无生产挂载、未选择的外泄）。
- 短暂容器：当且仅当容器及其凭证可丢弃时 `yolo` / `bypassPermissions` 可接受。

## 动手实践

`code/main.py` 模拟两阶段分类器。阶段1是提议动作上的便宜关键词规则；阶段2是更慢的多规则审查员。驱动程序输入短合成轨迹（安全动作、提示注入尝试、重复循环）并显示分类器捕获和遗漏的位置。

## 产出成果

`outputs/skill-permission-mode-picker.md` 将任务描述匹配到正确的权限模式、预算上限和所需隔离。

## 练习题

1. 运行 `code/main.py`。哪种合成动作类型阶段1从未标记但阶段2总是捕获？哪种两者都未捕获？

2. 扩展阶段1规则集以捕获特定已知不良形状（例如 `curl $ATTACKER/exfil`）。测量良性动作样本上的假阳性率。

3. 阅读Anthropic的"How the agent loop works"文档。列出 `default` 模式下智能体默认触及的每个外部状态。在无人值守运行 `autoMode` 前你需要单独门控哪些？

4. 设计24小时无人值守运行预算：`max_turns`、`max_budget_usd`、每工具上限、允许列表。证明每个数字。

5. 描述一个轨迹，其中每个单独动作被阶段1和阶段2批准，但组合行为未对齐。（第14课涵盖紧急停止开关和金丝雀token如何解决此问题。）

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|---|---|---|
| 权限模式 | "智能体能做多少" | 控制每次动作批准的七种命名策略之一 |
| plan模式 | "任何事前询问" | 智能体编写计划；用户执行前批准 |
| acceptEdits | "让它写文件" | 文件写入自动批准；shell执行仍提示 |
| autoMode | "自动批准" | 两阶段安全分类器；标记动作升级 |
| bypassPermissions | "完全YOLO" | 批准一切；用于短暂容器 |
| 阶段1分类器 | "快速token检查" | 提议动作上的单token规则；并行运行 |
| 阶段2分类器 | "深度审查" | 标记动作上的思维链推理 |
| 研究预览 | "非GA" | Anthropic对故障模式仍在映射的功能的框架 |
