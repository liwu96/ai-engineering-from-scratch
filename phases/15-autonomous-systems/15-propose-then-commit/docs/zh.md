# 人机循环：提议-然后-提交

> 2026年HITL的共识是具体的。它不是"智能体询问，用户点击批准"。它是提议-然后-提交：提议的动作以幂等键持久到持久存储；向审查员展示意图、数据血缘、触及的权限、爆炸半径和回滚计划；仅在积极确认后提交；执行后验证以确认副作用实际发生。LangGraph的 `interrupt()` 加PostgreSQL检查点、微软智能体框架的 `RequestInfoEvent`、Cloudflare的 `waitForApproval()` 都实现相同形状。规范故障模式是橡皮图章批准："批准？"未经审查就被点击。记录的缓解是带显式清单的挑战-响应。

**类型:** 学习
**语言:** Python (stdlib, 带幂等的提议-然后-提交状态机)
**前置要求:** 第15阶段 · 12 (持久执行), 第15阶段 · 14 (绊线)
**时间:** ~60分钟

## 问题背景

智能体采取行动。用户必须决定：批准与否。如果决定是即时的，可能不是审查。如果决定是结构化的，它慢但可信。工程问题是如何使结构化审查成为阻力最小的路径。

2023年时代的HITL模式是同步提示："智能体想发送邮件给X，正文Y——批准？"用户点击批准。每个人都感觉系统安全。实践中这个面被大量橡皮图章：用户快速批准、批准预测很少、当智能体出错时审计跟踪显示用户无法回忆的长期批准历史。

2026年模式——提议-然后-提交——将HITL移到持久基底，附加结构化元数据，并要求积极提交。每个托管智能体SDK发布一个版本：LangGraph `interrupt()`、微软智能体框架 `RequestInfoEvent`、Cloudflare `waitForApproval()`。API名称不同；形状相同。

## 概念讲解

### 提议-然后-提交状态机

1. **提议。** 智能体产生提议动作。持久到持久存储（PostgreSQL、Redis、Durable Object）。包括：
   - 意图（智能体为什么这样做）
   - 数据血缘（什么来源导致此提议）
   - 触及的权限（哪些范围/文件/端点）
   - 爆炸半径（最坏情况是什么）
   - 回滚计划（如果提交，如何撤销）
   - 幂等键（每提议唯一；重新提交返回相同记录）
2. **展示。** 审查员用所有元数据查看提议。审查员是人（非智能体自我审查）。
3. **提交。** 积极确认。动作执行。
4. **验证。** 执行后，副作用被读回并确认。如果验证步骤失败，系统处于已知不良状态并启动警报。

### 幂等键

没有幂等键，瞬态失败后的重试可以双倍执行已批准动作。具体示例：用户批准"从A转账$100到B"。网络闪烁。工作流重试。用户批准一次但转账执行两次。幂等键将批准绑定到单一、唯一的副作用；第二次执行是空操作。

这是Stripe和AWS API使用的相同幂等模式。将其用于智能体批准在微软智能体框架文档中明确说明。

### 持久性：为什么批准比进程更长久

批准候诊室是智能体不拥有的状态。工作流暂停（第12课）。批准到达时，工作流从该点精确恢复。这就是LangGraph将 `interrupt()` 与PostgreSQL检查点配对而不仅内存状态的原因——两天后的批准仍找到完整工作流。

### 橡皮图章批准和挑战-响应缓解

HITL的默认UI（"批准"/"拒绝"按钮）产生快速批准而无真正审查。记录的缓解：要求对具体问题积极回答才能启用批准按钮的挑战-响应清单。具体形状：

- "你理解这触及什么资源吗？[ ]"
- "你验证过爆炸半径可接受吗？[ ]"
- "如果失败你有回滚计划吗？[ ]"

非官僚主义本身——强制功能。无法勾选框的审查员要么要求澄清（升级），要么拒绝（安全默认）。Anthropic智能体安全研究明确将清单驱动的HITL作为橡皮图章批准模式的缓解。

### 什么算作 consequential

非每个动作都需要提议-然后-提交。2026年指导：

- **consequential 动作**（始终HITL）：不可逆写入、金融交易、外向通信、生产数据库更改、破坏性文件系统操作。
- **可逆动作**（有时HITL）：本地文件编辑、暂存环境更改、带清晰回滚的可逆写入。
- **读取和检查**（从不HITL）：读取文件、列出资源、调用只读API。

### 执行后验证

"提交运行"与"副作用发生"不同。网络分区和竞态条件可以产生认为成功而后端未持久的工作流。验证步骤提交后重新读取目标资源以确认。这与带 `RETURNING` 子句的数据库事务或AWS `PutObject` 后的 `GetObject` 相同模式。

### EU AI法案第14条

第14条要求欧盟高风险AI系统的有效人类监督。"有效"不是装饰性的。监管语言明确排除橡皮图章模式。带挑战-响应的提议-然后-提交是在微软智能体治理工具包合规文档中经受第14条审查的形状。

## 动手实践

`code/main.py` 在stdlib Python中实现提议-然后-提交状态机。持久存储是JSON文件。幂等键是(thread_id, action_signature)的哈希。驱动程序模拟三种情况：干净批准流程、瞬态失败后重试（不得双倍执行）、橡皮图章默认与挑战-响应流程。

## 产出成果

`outputs/skill-hitl-design.md` 审查提议的HITL工作流以提议-然后-提交形状，并标记缺失的元数据、幂等、验证或挑战-响应层。

## 练习题

1. 运行 `code/main.py`。确认已批准提议的重试使用持久记录而不重新执行。现在将幂等键更改为包含时间戳并显示重试双倍执行。

2. 用 `rollback` 字段扩展提议记录。模拟验证步骤失败的执行。显示回滚自动触发。

3. 阅读微软智能体框架的 `RequestInfoEvent` 文档。识别API包含而玩具引擎缺失的元数据字段。添加它并解释它防止什么。

4. 为特定动作（例如"发布到公共Twitter账户"）设计挑战-响应清单。审查员必须回答哪三个问题？为什么这三个？

5. 选择一个同步"批准？"提示足够的案例（无需持久存储）。解释为什么，并命名你接受的风险类别。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|---|---|---|
| 提议-然后-提交 | "两阶段批准" | 持久提议 + 积极提交 + 验证 |
| 幂等键 | "重试安全令牌" | 每提议唯一；第二次执行空操作 |
| 数据血缘 | "来源" | 导致提议的特定来源内容 |
| 爆炸半径 | "最坏情况" | 如果动作出错的效应范围 |
| 橡皮图章 | "快速批准" | 未经真正审查就点击"批准" |
| 挑战-响应 | "强制清单" | 审查员必须积极确认具体问题 |
| RequestInfoEvent | "MS智能体框架原语" | 带结构化元数据的持久HITL请求 |
| `interrupt()` / `waitForApproval()` | "框架原语" | LangGraph / Cloudflare的等效形状 |
